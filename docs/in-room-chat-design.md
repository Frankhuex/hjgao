# 房间内聊天交互与网络设计

## 目标与范围

本方案为当前房间增加文本聊天功能。玩家在移动模式和打牌模式下都可以通过 `T` 打开或关闭左侧聊天面板。聊天面板默认只显示消息，不抢占键盘焦点；只有打牌模式下点击输入框后，键盘才进入聊天输入状态。收到其他玩家的实时消息时，无论聊天面板是否打开，右上角都会显示限时通知横幅。

本文把“所有历史消息”定义为当前服务器房间会话内的消息。新玩家加入后会收到此前的聊天记录，服务器重启、返回主菜单或退出房间后清空记录。该范围可以避免无限增长的内存占用，也符合当前项目没有账号和持久化存储的现状。

本轮设计不包含私聊、频道、系统公告、消息撤回、玩家屏蔽、语音、聊天历史持久化和房间外聊天。

## 现有约束

当前玩家模式由 `Player.player_status` 管理，包含 `MOVE` 和 `CARD`。空格键由 `player.gd` 切换模式，鼠标在 `MOVE` 模式下被捕获，在 `CARD` 模式下可见。

当前全局限定键由 `game.gd` 的 `_input()` 处理，`Q` 切换卡牌说明，`Esc` 打开或关闭暂停菜单。输入框聚焦时必须在这些逻辑之前接管键盘事件，否则空格会切换模式，`Q` 会切换卡牌说明，`T` 会关闭面板。

Godot 4.7.2 的 `TextEdit` 支持多行文本、占位文字、换行模式和输入法，但当前版本没有 `max_length` 属性。消息长度、行数和空白处理必须由脚本在发送前处理，并由服务器再次校验。

当前 `ENetMultiplayerPeer` 使用默认单通道可靠 RPC。聊天建议使用独立可靠通道，避免连续聊天消息和较大的历史快照阻塞牌库、卡牌操作等游戏消息。

## 组件划分

| 组件 | 职责 |
| --- | --- |
| `ChatPanel.tscn` | 左侧聊天面板、消息历史、输入框和发送按钮 |
| `chat_panel.gd` | 面板显示、文本追加、滚动、聚焦状态、发送按钮和本地输入事件 |
| `ChatBanner.tscn` | 右上角单条消息横幅的视觉结构 |
| `chat_banner.gd` | 横幅进入、停留、退出动画和生命周期 |
| `NotificationStack` | 管理多条横幅的顺序、超时、数量上限和整体定位 |
| `GameSession` | 鼠标点击判定、聊天热键分流、玩家输入启停、RPC、服务器历史、限流和清理 |
| `Player` | 保持现有模式逻辑，聊天聚焦期间由 `GameSession` 调用 `set_input_enabled(false)` 暂停玩家按键 |
| `Util` | 提供纯函数形式的消息清洗、换行标准化和长度限制，便于测试 |

聊天 UI 不应直接发送网络 RPC。`ChatPanel` 只发出 `send_requested(content)` 信号，`GameSession` 决定在当前节点是服务器还是客户端，并调用对应网络入口。这样玩家名始终由服务器附加，客户端无法伪造发送者名称。

## 界面设计

聊天面板使用新的 `CanvasLayer`，层级设置为 50，低于现有暂停界面的层级 100。这样暂停菜单会覆盖聊天面板，聊天面板不会盖住暂停按钮、确认框和文件选择框。

面板固定在屏幕左侧，使用左右各 16 像素的外边距，宽度建议为 300 至 340 像素。高度覆盖窗口中部的较大区域，底部保留输入区，历史消息区域占剩余空间。窗口尺寸变化时由锚点和容器布局自动调整。

| 节点 | 类型 | 关键设置 |
| --- | --- | --- |
| `ChatPanel` | `PanelContainer` | 左侧锚定，固定宽度，默认隐藏 |
| `ChatTitle` | `Label` | 文本为“聊天” |
| `MessageHistory` | `RichTextLabel` | `bbcode_enabled = false`，`scroll_following = true`，允许选择文本 |
| `InputRow` | `HBoxContainer` | 位于面板底部 |
| `MessageInput` | `TextEdit` | 多行输入，占位文字为“输入消息…”，最小高度约 72 像素 |
| `SendButton` | `Button` | 文本为“发送”，鼠标点击发送 |

`MessageHistory` 显示纯文本，每一条消息严格使用 `玩家名称: 消息内容` 的格式。半角冒号后保留一个半角空格。消息内容中的换行直接保留，后续行不重复玩家名称。每条消息之间追加一个换行作为分隔。

消息历史不使用 BBCode。玩家名称和消息内容都可能包含特殊字符，必须按纯文本追加，避免标记注入和意外富文本渲染。

`MessageInput` 使用点击聚焦模式，不允许通过 Tab 自动获得焦点。`SendButton` 不允许键盘焦点，只响应鼠标点击。聊天面板可见时，面板区域拦截鼠标事件，避免点击历史消息区域时穿透到 3D 卡牌或牌堆。

面板默认关闭。按 `T` 打开后只显示历史消息和输入区，输入框不带光标，不改变当前玩家模式，也不改变鼠标捕获状态。

右上角通知区域独立于左侧聊天面板。聊天面板关闭时通知仍然显示，聊天面板打开时两者同时存在。通知区域位于现有暂停按钮下方，避免遮挡右上角的暂停入口。

## 状态模型

聊天面板有三个状态：

| 状态 | 面板可见 | 输入框聚焦 | 玩家原按键 | 说明 |
| --- | --- | --- | --- | --- |
| `CLOSED` | 否 | 否 | 正常 | 初始状态 |
| `OPEN_IDLE` | 是 | 否 | 正常 | `T` 打开后的默认状态 |
| `TYPING` | 是 | 是 | 暂停 | 只有打牌模式点击输入框后进入 |

玩家模式 `MOVE` 或 `CARD` 与聊天状态相互独立。关闭聊天不会切换玩家模式，取消输入聚焦也不会自动切回移动模式。

进入 `TYPING` 时调用 `local_player.set_input_enabled(false)`，保证空格、移动输入和玩家自己的 `_input()` 不执行。退出 `TYPING` 时，如果仍在房间内、暂停界面未打开、模态对话框未打开，则调用 `local_player.set_input_enabled(true)`。

打开暂停菜单或更换卡组、清场等模态对话框前，必须主动释放聊天输入焦点。聊天面板保持可见，草稿保留，返回游戏后处于 `OPEN_IDLE`。

## 键鼠交互

| 当前状态 | 输入 | 结果 | 是否消费事件 |
| --- | --- | --- | --- |
| `CLOSED` 或 `OPEN_IDLE` | `T` | 打开或关闭聊天面板 | 是 |
| `OPEN_IDLE` | `Space` | 保持现有行为，切换移动模式与打牌模式 | 是，由 `Player` 处理 |
| `OPEN_IDLE` | `Q` | 保持现有行为，切换卡牌说明 | 是 |
| `OPEN_IDLE` | `Esc` | 保持现有行为，打开或关闭暂停菜单 | 是 |
| `OPEN_IDLE` 且打牌模式 | 点击输入框 | 进入 `TYPING` | 由 `TextEdit` 处理 |
| `OPEN_IDLE` 且移动模式 | 点击输入框 | 不进入输入状态，输入框保持无焦点 | 是，面板拦截点击 |
| `TYPING` | 普通字符、空格、`Q`、`T` | 作为文字输入 | TextEdit 处理 |
| `TYPING` | `Enter` 或小键盘 `Enter`，无 Shift | 发送消息，清空输入框，保持 `TYPING` | 是 |
| `TYPING` | `Shift + Enter` | 插入换行，不发送 | TextEdit 处理 |
| `TYPING` | `Esc` | 释放输入焦点，聊天保持可见，并打开暂停菜单 | 是 |
| `TYPING` | 点击输入框外 | 释放输入焦点，切换到 `OPEN_IDLE` | 否，鼠标事件继续交付正常目标 |

`Esc` 永远不关闭聊天面板，也不负责取消聊天。它的职责保持为暂停菜单。输入状态下按 `Esc` 时先结束输入状态，再调用现有暂停菜单逻辑，草稿保留。

`T` 只有在 `CLOSED` 和 `OPEN_IDLE` 状态下关闭面板。处于 `TYPING` 时，`T` 是普通字符。玩家若要关闭面板，应先点击输入框外取消聚焦，再按 `T`。

点击输入框外时只取消聊天焦点，不改变玩家模式。该点击如果落在游戏世界、卡牌或牌堆上，仍按现有规则继续处理。点击落在聊天面板其他区域时，由面板消费，不穿透到游戏世界。

移动模式下鼠标处于捕获状态，因此输入框无法被鼠标点击。玩家需要先用空格切换到打牌模式，再点击输入框。该限制与当前两种模式的鼠标行为一致。

发送按钮的点击会先让输入框失去焦点，然后发送当前内容。通过发送按钮发出的消息使用 `OPEN_IDLE` 作为最终状态；通过回车发送的消息保持 `TYPING`，便于连续输入。

## 输入事件优先级

`GameSession._input()` 需要按以下顺序处理事件：

1. 暂停界面或模态对话框可见时，聊天不响应 `T`，并确保输入框没有焦点。
2. 输入框有焦点且发生鼠标点击时，先判断点击位置是否在输入框外。外部点击释放焦点，但不消费事件。
3. 输入框有焦点且收到 `Esc` 时，释放焦点并执行暂停菜单逻辑。
4. 输入框有焦点且收到无 Shift 的 `Enter` 时，发送并消费事件，避免 `TextEdit` 同时插入换行。
5. 输入框有焦点且收到其他键盘事件时，`GameSession` 直接返回，由 `TextEdit` 处理文字、空格、`Q`、`T` 和 `Shift + Enter`。
6. 输入框未聚焦时，才处理 `T` 开关、`Q` 卡牌说明和 `Esc` 暂停菜单。

`Player._input()` 保持原有空格切换逻辑。聊天聚焦期间通过 `input_enabled = false` 阻止它处理空格，避免依赖节点执行顺序。

点击判定以 `MessageInput.get_global_rect().has_point(mouse_event.position)` 为准。点击发送按钮不属于输入框内部，因此会先取消焦点，再触发按钮发送。

## 输入清洗

客户端发送前和服务器接收后都执行同一套规则。建议将纯函数放在 `Util.sanitize_chat_message()`，返回清洗后的文本和是否有效。

1. 把 `\r\n` 和独立的 `\r` 统一为 `\n`。
2. 把制表符替换为空格。
3. 移除 NUL 和其他不可显示控制字符，保留换行。
4. 删除消息首尾空白和首尾空行。
5. 清洗后为空的消息不发送。
6. 最大长度为 500 个 Unicode 字符。
7. 最大行数为 8 行。
8. 超长或超行消息由客户端阻止发送，服务器再次校验并丢弃不合法消息。

消息内容允许中文、Emoji、标点和内部换行。玩家名称继续使用服务器已有的 `player_names` 映射，聊天消息不接收客户端提交的名称字段。

## 网络协议

聊天使用服务器权威 RPC。客户端只提交消息内容，服务器从连接信息获得 `peer_id`，再从 `player_names` 获得玩家名称，并生成广播消息。

| RPC | 注解 | 作用 |
| --- | --- | --- |
| `submit_chat_message(content)` | `any_peer`、`call_remote`、`reliable`、默认通道 | 客户端请求发送消息 |
| `request_chat_history()` | `any_peer`、`call_remote`、`reliable`、默认通道 | 客户端请求完整房间历史 |
| `receive_chat_history(history)` | `authority`、`call_remote`、`reliable`、默认通道 | 服务器只向请求者发送历史快照 |
| `receive_chat_message(sender_id, sender_name, content)` | `authority`、`call_local`、`reliable`、默认通道 | 服务器广播已确认消息 |

服务器收到 `submit_chat_message()` 后执行以下步骤：

1. 确认节点是服务器且房间仍处于活动状态。
2. 使用 `multiplayer.get_remote_sender_id()` 获取发送者，不接受客户端传入的玩家 ID。
3. 从 `player_names` 获取服务器确认的显示名称。
4. 清洗并校验消息内容。
5. 执行每名玩家独立的频率限制。
6. 把消息追加到服务器历史。
7. 调用 `receive_chat_message.rpc()` 广播给所有客户端，并通过 `call_local` 同时更新主机界面。

历史记录建议最多保留 200 条，每条内容仍受 500 字符和 8 行限制。每条历史项保存 `sender_id`、`sender_name` 和 `content`，不保存客户端时间。

客户端连接成功后请求一次历史。`receive_chat_history()` 使用替换模式更新本地缓存，多次请求不会产生重复消息。请求和广播使用同一条可靠有序通道，因此服务器先收到的历史请求会先收到快照，随后消息按发送顺序到达。

服务器为每个 `peer_id` 只响应一次历史快照请求。该限制在玩家断开时清除，避免已认证客户端反复拉取完整历史造成带宽占用。

独立 ENet 通道是长期优化方向。首轮实现经过多客户端重连测试后使用默认可靠通道 0，因为当前 Godot 4.7.2 与 ENet 的独立通道组合在后加入连接上出现了偶发发送丢失。聊天历史限制为 200 条，当前消息量下可以安全共享默认可靠队列。

后续如果聊天量明显增加，可以重新评估独立通道，并在迁移前补充多人重连、后加入和历史快照的专项回归测试。

## 频率限制

服务器为每个 `peer_id` 维护令牌桶，建议容量为 5，每秒补充 1 个令牌。发送消息消耗 1 个令牌，令牌不足时服务器丢弃该消息。

频率限制只作用于消息接受阶段，不广播错误弹窗。正常输入的玩家不会感知限制，持续刷屏不会耗尽服务器或客户端资源。玩家断开时立即删除其令牌桶记录。

## 历史与显示

服务器维护房间会话历史，所有客户端维护只读显示缓存。聊天面板打开或关闭只影响显示，不清除历史或草稿。

新消息到达时，如果消息历史已经贴近底部，则自动滚动到最新消息。如果用户主动向上滚动，新的消息不强制抢回滚动位置。用户重新滚动到底部后恢复自动跟随。

聊天历史上限与服务器一致。超过 200 条时删除最旧记录。客户端收到的历史快照和实时消息使用相同的纯文本渲染函数，保证主机、普通客户端和后加入客户端显示格式一致。

消息在服务器接受后才会广播，显示文本由服务器名称和已清洗内容拼接。玩家离开后，历史中仍保留该玩家曾经发送的消息，玩家名册变化不会重写历史名称。

## 新消息通知

### 触发条件

只有客户端收到实时 `receive_chat_message()` 广播时才创建通知。服务器发送的历史快照只填充聊天历史，不为旧消息补发横幅。本地玩家自己发送的消息已经出现在聊天历史中，也不创建通知。

通知触发与聊天面板状态无关。`CLOSED`、`OPEN_IDLE` 和 `TYPING` 三种状态都显示通知。通知不得获取输入焦点，不得改变鼠标模式，也不得中断正在进行的聊天输入。

### 视觉与布局

通知栈固定在屏幕右上角，右侧边距 16 像素，顶部起点 88 像素，确保不会覆盖现有的 `PauseButton`。单条横幅宽度约 240 像素，高度由预览内容决定，通常为 36 至 40 像素。多条横幅使用垂直排列，间距 8 像素。

通知顺序与消息到达顺序一致。最旧的消息位于最上方，新消息追加到最下方。最上方通知的 10 秒生命周期结束后先退出，剩余通知整体向上收拢。

单条横幅显示与聊天历史相同的格式，第一行使用 `玩家名称: 消息内容`。预览区域最多显示两行，消息中的换行在横幅中转换为空格，超出部分使用省略号。横幅字号固定为 16，避免通知在游戏画面中显得过大。完整的多行消息仍然保留在聊天历史中。

通知栈的最大可见数量固定为 2。超过上限时立即移除最上方的最旧通知，即使它的 10 秒时间尚未结束。后续新增的消息会替换可见消息，保证横幅区域保持简短。

通知栈和横幅视觉设置为不接收鼠标事件。玩家点击通知区域时，事件继续传递给下方游戏界面，暂停按钮和卡牌操作不受影响。通知所在的 `CanvasLayer` 层级低于暂停界面，暂停菜单或模态对话框打开时不会显示在其上方。

### 单条生命周期

单条通知包含以下状态：

| 状态 | 行为 |
| --- | --- |
| `ENTERING` | 从最终位置下方 14 至 18 像素开始，透明度从 0 到 1，向上移动并浮现 |
| `VISIBLE` | 保持最终位置和完整透明度，开始 10 秒计时 |
| `EXITING` | 最上方通知淡出，并向上移动约 8 像素后删除 |
| `REMOVED` | 从通知栈移除，释放动画引用 |

进入动画建议持续 0.18 秒，使用 `EASE_OUT` 和 `TRANS_SINE`。退出动画建议持续 0.12 秒。动画过程不使用缩放、弹跳或大幅位移，保持与当前游戏界面一致的简洁观感。

10 秒计时从进入动画结束时开始，保证每条通知都有完整的可见停留时间。计时使用单调毫秒时间或等价机制，避免受到帧率波动影响。如果项目以后启用 `SceneTree.paused`，通知管理器应设置为始终处理计时和动画。

### 多消息动画

通知栈使用容器维护最终顺序，每条横幅外层有一个固定高度的布局槽，内层视觉负责位移和透明度动画。这样动画不会破坏 `VBoxContainer` 的最终布局。

新消息到达时，如果栈已满，三条动画同时启动：最上方通知向上淡出，第二条通知向上滑动到第一条的位置，第三条通知在底部从下方约 16 像素向上浮现。第二条的滑行距离等于一条横幅高度加间距；淡出完成后旧槽位从容器删除，第二条回到槽位原点，容器把第三条排到第二位。这样视觉上第三条会落到原第二条的位置。

如果栈未满，只在底部创建布局槽，并把内层视觉初始位置放在最终位置下方约 16 像素。新视觉在向上移动并浮现的过程中，由较后的绘制顺序覆盖在旧横幅上方。动画结束后，内层视觉回到槽位原点，多条通知保持稳定的垂直排列。

快速连续消息按到达顺序进入待处理队列。每次过渡完成后只取队首一条继续展示，通知不丢序；完整消息始终先写入聊天历史。

如果前一条通知仍在进入或退出动画中，新通知继续追加到栈底部。每条横幅只保留一个进入 Tween 和一个退出 Tween，新动画开始前必须停止旧 Tween，避免同一节点同时被多个动画写入属性。

### 与聊天状态的协作

聊天面板关闭时，实时消息只显示通知横幅。聊天面板打开但仍未聚焦时，通知和完整消息同时更新。输入框处于 `TYPING` 时，通知正常出现，输入焦点和光标位置保持不变，回车和 `Shift + Enter` 的语义不变。

玩家向上滚动查看历史时，新消息通知仍然出现，但聊天历史不强制滚动到底部。通知消失不代表消息丢失，完整内容始终保存在聊天历史中。

返回主菜单、断开连接或服务器关闭时，通知栈立即清空，所有计时器和 Tween 停止。重新进入房间后不会恢复上一个房间的通知。

## 与暂停、卡牌和牌库的协作

暂停界面打开前释放聊天焦点，但聊天面板保留在暂停界面下方。关闭暂停界面后，聊天处于 `OPEN_IDLE`，不会自动恢复输入焦点。

更换卡组确认框、清空桌面确认框和卡组查看界面打开前也释放聊天焦点。聊天开关在这些模态界面存在时不响应键盘热键。

聊天输入聚焦期间，鼠标在打牌模式下仍然可见。点击聊天面板内部只作用于聊天控件。点击面板外部可以恢复卡牌或牌堆交互，并在同一次点击中取消聊天焦点。

聊天不改变 `Player.player_status`，不改变 `Player.input_enabled` 之外的玩家状态，也不修改牌堆权限或多人同步数据。

## 失败与边界处理

| 场景 | 处理 |
| --- | --- |
| 空白消息 | 不发送，输入内容保留 |
| 只有空行或空格 | 不发送，输入内容保留 |
| 超长消息 | 客户端阻止发送，服务器丢弃 |
| 超过 8 行 | 客户端阻止发送，服务器丢弃 |
| 发送期间断开 | 清理聊天缓存、草稿和输入焦点 |
| 历史请求前断开 | 服务器忽略目标，不创建无效历史 |
| 重复历史快照 | 客户端替换缓存，不追加重复项 |
| 玩家名称不存在 | 服务器使用 `玩家<peer_id>` 作为兜底名称 |
| 发送按钮点击 | 先取消焦点，再发送有效内容 |
| 聊天面板关闭 | 草稿保留，历史保留 |
| 自己发送消息 | 更新聊天历史，不创建通知 |
| 收到历史快照 | 更新聊天历史，不创建通知 |
| 短时间内连续消息 | 按到达顺序堆叠，超过 2 条时提前移除最旧通知 |
| 通知正在动画时又收到消息 | 新通知追加到底部，不打断输入状态 |
| 通知区域被点击 | 鼠标事件穿透到游戏界面 |
| 返回主菜单 | 面板关闭，历史、草稿和限流记录全部清空 |
| 暂停菜单打开 | 不得保留聊天输入焦点 |

## 测试计划

消息清洗测试覆盖 CRLF、制表符、首尾空格、空消息、500 字符边界、8 行边界、中文和 Emoji。

输入状态测试覆盖 `T` 开关、空格模式切换、`Q` 卡牌说明、输入状态下字符输入、`Shift + Enter` 换行、回车发送、点击外部取消焦点、发送按钮发送和 `Esc` 打开暂停。

网络测试使用一个主机和两个客户端。主机发送消息后两个客户端都按 `名称: 内容` 格式收到；两个客户端互相发送消息；后加入的第三个客户端收到完整房间历史。

通知测试确认其他玩家消息在聊天面板关闭、打开和输入时都显示横幅。本地消息和历史快照不显示通知。收到第 3 条实时消息时，最旧通知按规则立即退出。

动画测试确认新通知从下方向上进入并淡入，顶部通知约 10 秒后淡出，剩余通知向上收拢。通知出现和消失不改变玩家模式、暂停状态、聊天焦点和聊天滚动位置。

安全测试覆盖客户端伪造名称、超长消息、超行消息、空白消息和短时间连续发送。服务器应使用真实 `peer_id` 和服务器名称，拒绝非法内容并执行限流。

交互回归测试确认聊天聚焦时空格不切换模式、`Q` 不切换说明、`T` 不关闭面板。取消聚焦后这些按键立即恢复原功能。

界面测试覆盖移动模式和打牌模式、聊天打开和关闭、暂停菜单覆盖聊天面板、历史自动滚动、多行消息显示和不同窗口尺寸下的面板边界。

## 验收标准

移动模式和打牌模式都可以用 `T` 打开和关闭聊天面板。打开面板不会自动聚焦，空格、`Q`、`T` 和暂停行为在未聚焦时保持原样。

打牌模式下点击输入框后，空格、`Q`、`T` 等按键只进入文本。回车发送，`Shift + Enter` 换行，发送后消息按 `玩家名称: 内容` 显示。点击输入框外取消聚焦，随后空格恢复模式切换，`T` 可以关闭面板。`Esc` 始终用于打开暂停菜单，不负责关闭聊天。

服务器权威保存并广播聊天记录，新加入玩家可以获得当前房间历史。玩家名称取自服务器已确认的名称映射，非法消息和刷屏请求不会影响其他玩家。

收到其他玩家的实时消息时，无论聊天面板是否打开，右上角都会按到达顺序显示通知横幅。每条横幅完整停留约 10 秒，最上方通知先消失，连续消息不破坏输入焦点、玩家模式或游戏鼠标交互。
